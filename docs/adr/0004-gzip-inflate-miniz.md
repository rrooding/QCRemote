# ADR 0004: miniz (tinfl-only) for issue #6's generic gzip inflate, run off the usbh thread

Date: 2026-10-31
Status: Accepted

## Context

qc-mcp's `protocol.py::decode_message()` treats gzip compression as a generic property of
the message-decode layer: it checks whether a message's protobuf blob *starts with*
`\x1f\x8b\x08` (gzip magic + deflate method) and transparently inflates when it does,
regardless of which command the message carries. Issue #6 asks for the same thing here, at
the same seam `QcMessage.hpp::decodeMessage()` already calls out: right after an
HID-reassembled message is split into trailer + protobuf blob.

Two constraints shape the implementation more than the detection logic itself does:

- **Where it can run.** `QcSession::handleMessage()` executes on Zephyr's own internal
  `usbh` thread (`CONFIG_USBH_STACK_SIZE`, 1536 bytes - see that function's own comment),
  which already overflowed once this session from a single added `LOG_INF` call.
  `tinfl_decompress()`'s own working state (see below) is too large for that budget
  regardless of how carefully it's called, and running CPU-bound decompression on the same
  thread that services the USB host controller's report timing is a bad idea independent of
  stack math. Inflate cannot run there.
- **How big a decompressed payload to accept.** Issue #33 owns the overall firmware memory
  budget and is still open; `QcHidBridge.hpp`'s `kReassemblyCapacity = 4096` is explicitly a
  placeholder pending that work. This issue needs its own bounded answer now without
  pre-empting #33.

A separate, pre-existing gzip use (`ModelRepo`'s `model_repo_payload`: a gzip+tar of
`ModelRepo.xml` inside a protobuf `bytes` field, per `catalog.py`) is out of scope here per
the issue's own scope notes - this ADR and its implementation only cover the generic,
whole-protobuf-blob compression `decode_message()` handles.

### Library choice

The issue suggests "a small embedded-friendly library (e.g. miniz)". miniz
(https://github.com/richgel999/miniz, MIT license) ships `tinfl` (inflate) and `tdefl`
(deflate) as largely independent low-level APIs, plus a zlib-compatible wrapper and a
ZIP-archive layer on top - all four combined into one CMake target by miniz's own
`CMakeLists.txt`. Only `tinfl_decompress()` (raw deflate decoding) is needed here; the
deflate/zip/zlib-wrapper code and miniz's own build system (which calls `project()` and
assumes a standalone/shared-library build with a `generate_export_header()` step) add
nothing and don't nest cleanly inside a Zephyr app's CMake. Pure-header alternatives
(`stb_inflate`-style single-file decoders) exist but are less battle-tested than miniz's
`tinfl`, which is widely deployed (used by, among others, Unity's and Godot's asset
pipelines) and has a cleaner low-level API for exactly this "give me a bounded output buffer,
tell me if it didn't fit" use case than most alternatives.

## Decision

Vendor miniz 3.0.2's source tree via CMake `FetchContent_Populate` (not
`FetchContent_MakeAvailable`: deliberately skips `add_subdirectory`-ing miniz's own
`CMakeLists.txt`) and compile only `miniz_tinfl.c` ourselves, with `MINIZ_NO_STDIO`,
`MINIZ_NO_MALLOC`, `MINIZ_NO_TIME`, `MINIZ_NO_DEFLATE_APIS`, `MINIZ_NO_ARCHIVE_APIS`, and
`MINIZ_NO_ZLIB_APIS` stripping the rest of miniz's declarations down to just
`tinfl_decompress()` and its supporting types. `miniz_export.h` (normally generated by
miniz's own CMake for a shared-library build) is our own one-line stub
(`firmware/app/third_party/miniz/miniz_export.h`) since there's no shared-library boundary
here. CRC-32 (needed to validate the gzip trailer) is hand-rolled in `QcGzip.hpp` rather than
linking miniz's `mz_crc32()`, which lives in `miniz.c` - a file we don't want to compile at
all, since it declares the deflate/zip code alongside it.

`QcGzip.hpp::inflate()` parses the gzip member header itself (RFC 1952: fixed 10-byte header,
optional FEXTRA/FNAME/FCOMMENT/FHCRC fields, 8-byte CRC32+ISIZE trailer), calls
`tinfl_decompress()` on the raw deflate payload into a caller-supplied output buffer, and
**strictly validates** the trailer's CRC32 and length against the decompressed output. This
is stricter than qc-mcp's own `gunzip()` helper, which falls back to a non-validating
streaming decompress (no CRC/length check) when its first, strict `zlib.decompress()`
attempt raises on a truncated or corrupted stream - that fallback is deliberately **not**
reproduced here. A firmware decoder has no good way to flag "this is probably-complete but
unverified data" to whatever would consume it next; failing closed on anything
malformed/truncated/CRC-mismatched, and letting the caller treat the message as dropped
(same as `HidReassembler::Status::Overflow`/`Malformed` already do), is the safer default on
a device with no interactive user to notice a wrong answer.

`QcSession::handleMessage()` (still on the `usbh` thread) only adds the cheap part: a 3-byte
magic check (`gzip::hasMagic()`) on `decoded->protoBytes`, right after `decodeMessage()`
splits it out. If present, it hands the compressed bytes to a new `QcGzipInflater`, which
owns a single dedicated worker thread (4096-byte stack, priority between the handshake's and
the heartbeat's) and a single in-flight mailbox slot (sized to
`gzip::kMaxCompressedInputSize = 4096`, matching `kReassemblyCapacity`); `submit()` is a
bounded `memcpy` + semaphore signal, cheap enough to call from `usbh`. The actual
`gzip::inflate()` call, and the only logging of its outcome, happen on that dedicated thread.
A second compressed message arriving before the first finishes is dropped rather than queued
- acceptable for now since there's no real consumer of the decompressed bytes yet (see
Consequences).

Output is capped at `gzip::kMaxInflatedSize = 16384` bytes (4x the compressed input cap):
generous for the gzip ratios (commonly 3-6x) typical of this protocol's text/protobuf
payloads, while still bounding a maliciously-crafted "zip bomb" style input to a clean
`OutputTooLarge` failure instead of unbounded work. This is independent of, and far smaller
than, `ModelRepo`'s internal catalog payload (~675KB uncompressed, confirmed from qc-mcp's
own `ModelRepo.xml` fixture) - decompressing/untarring that catalog is explicitly out of
scope for this issue and would need #33's broader memory-budget exercise (and probably
streaming decompression) regardless of this constant.

## Consequences

- **Measured cost on `frdm_rw612`** (clean `west build`, this change vs. the same build at
  `434439e`, the commit immediately before this one): **FLASH +4728 B** (76064 B -> 80792 B,
  0.11% -> 0.12% of the board's 64MB external flash - negligible), **RAM +33160 B**
  (56736 B -> 89896 B, 5.77% -> 9.14% of the board's 960KB SRAM). The RAM increase is almost
  entirely the module's own static buffers, not code: `tinfl_decompressor`'s Huffman-table
  struct (~8.2KB), the 4096-byte compressed-input mailbox, the 16384-byte decompressed-output
  buffer, and `QcGzipInflater`'s own 4096-byte thread stack account for essentially all of
  it. `kMaxInflatedSize` is the single largest knob here if #33's eventual budget needs this
  shrunk.
- No consumer reads the decompressed bytes yet - there's no `ModelRepo` (or other) message
  handler in this firmware at all (issue #5 Tier 2 / #9). `QcGzipInflater` currently just logs
  the outcome (size on success, `InflateError` on failure). This is deliberately incomplete:
  the generic detect+inflate step this issue asks for now exists and is exercised against
  real traffic shape via its own Ztest fixtures, ready for a real handler to read from once
  one exists, rather than inflating into a buffer nothing reads.
- Single in-flight mailbox slot means back-to-back compressed messages faster than one
  inflate cycle apart will drop the later one. Not a concern today (no compressed traffic
  flows at all yet - see the issue's own note that PR #56 only observed uncompressed
  `Version` replies), but worth revisiting alongside #33 if/when a real consumer needs a
  stronger guarantee.
- Not exercised against real device traffic. The device doesn't currently send anything
  compressed (firmware doesn't yet send the state `READ`s that would trigger a `ModelRepo`
  reply - that's #9), so this can't be validated against real hardware until #9 lands, and
  possibly not fully even then without a #5 Tier 2 handler to confirm the decompressed bytes
  decode as the expected protobuf message.
